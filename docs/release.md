# Release artifacts and verification

Durable record of the release surface: what is shipped, how it is verified, and which
platforms are promised. Platform evidence and baselines live here and in
`docs/adr/0003-native-release-matrix.md`; the two documents are kept in agreement.

## Artifact layout

Release archives are named `brave-search-<version>-<os>-<arch>.tar.gz` (for example
`brave-search-1.2.0-macos-aarch64.tar.gz`) and contain exactly one top-level directory named
like the archive stem:

```text
brave-search-<version>-<os>-<arch>/
├── bin/brave-search                        native executable, mode 0755
├── completions/brave-search.bash           packaged Bash completion
├── completions/brave-search.zsh            packaged Zsh completion
├── lib/brave-search-client-<version>.jar   published library
├── lib/brave-search-client-<version>-sources.jar
├── lib/brave-search-client-<version>-javadoc.jar
├── skills/brave-search/SKILL.md            distributable agent skill
├── schemas/v1/*.schema.json                machine-output JSON schemas for agents
├── sbom/bom.json                           runtime-only CycloneDX SBOM
├── README.md
└── LICENSE
```

The JARs are exactly the published Maven artifacts (`io.amscotti:brave-search-client`), so a
Java consumer can take the library straight from an unpacked release. Archives are
reproducible: sorted entries, fixed timestamps, pinned modes — two builds of one tree produce
byte-identical archives and SBOMs.

## Checksums

Each platform build produces a staging `SHA256SUMS` covering exactly the artifacts beside
it — that platform's archive and its SBOM — one `<sha256>  <filename>` line per artifact,
sorted by name, generated with runner-native tooling and re-verified by the release
verification legs and the local `ReleaseArchiveVerificationTest`, which fail on any
mismatch, missing entry, or extra artifact. The published release carries **one aggregate
`SHA256SUMS`** instead: the single privileged publisher generates it after every platform
artifact has landed, covering every archive and SBOM of the release across platforms, and
uploads it exactly once. Per-platform checksum files never upload as release assets —
their basenames would collide — so the aggregate is the only checksum manifest installers
see.

## SBOM scope

The shipped SBOM is **production-runtime-only**. It is generated by the pinned
`org.cyclonedx.bom` 3.4.0 plugin as an application-type document scoped to exactly the
`runtimeClasspath` configuration — the CycloneDX direct task with `includeConfigs`
containing only `runtimeClasspath` and `projectType APPLICATION` — so test, test-fixtures,
and annotation-processor dependencies (JUnit, ArchUnit, the JSON Schema validator,
picocli-codegen) never appear, while picocli and Jackson, which run in production, always
do. The SBOM is emitted without a serial number for byte-reproducibility, ships inside the
archive at `sbom/bom.json` and beside it as `brave-search-<version>-<os>-<arch>.sbom.json`,
and its scope is asserted by test.

## Local verification

The Gradle-level proof of the release surface runs as part of `check` on every host with a
supported release triple (macOS and Linux; the archive is cut for the host that builds it,
so a host without a triple — the pinned toolchains include windows-x64 — fails the
packaging itself, and its `test`/`check` fail with it because the verification below is
wired into `test`):

- `releaseArchive` packages the archive (native binary, docs, completions, skill, machine
  schemas, published JARs, SBOM);
- `releaseSbom` places the SBOM beside the archive;
- `sha256Sums` writes `SHA256SUMS` over the release directory;
- `io.amscotti.bravesearch.release.ReleaseArchiveVerificationTest` (the unit test suite;
  the build wires the packaged archive and release directory into `test` through system
  properties after `sha256Sums`) unpacks the real archive with the platform `tar`, asserts
  the naming form, the single top-level directory, the executable bit of `bin/brave-search`,
  a clean `--version` run whose printed version matches the archive name, full `SHA256SUMS`
  coverage with matching digests, the runtime-only SBOM scope, the packaged machine
  schemas, and that the SBOM inside the
  archive is byte-identical to the one staged beside it — both renderings of one
  deterministic SBOM build.

Determinism is proven at two depths. The cheap pin runs in every unit suite: the archive's
`sbom/bom.json` and the staged `<stem>.sbom.json` must be byte-identical, and the SBOM
carries no serial number. The full convention — two builds of one tree produce byte-identical
archives and SBOMs, sorted entries, fixed timestamps, pinned modes — is proven by hand
before any release: rebuild from a clean output directory and compare digests of both
artifacts; a drifting digest stops the release until explained.

A tampered-dependency drill, `./gradlew dependencyTamperProof`, proves the committed
dependency verification end to end: the child Gradle build runs with `GRADLE_USER_HOME`
pointed at a scratch home (so the real caches are never read or mutated) and resolves the
runtime coordinates against an honest mirror of the cached artifacts (must succeed), then
against a one-byte-corrupted copy of `picocli-4.7.7.jar` (must fail dependency
verification). Evidence — including the isolated home path — is written to
`build/reports/dependency-tamper-proof/evidence.txt`. The release workflow runs the same
drill as its own pre-publish leg (`tamper-drill`) on the tagged sources, and the privileged
publisher waits for it beside the three platform verifications; `WorkflowContractTest` pins
the leg and the dependency.

### Native image contributor policy

The native build stays honest by construction: image building runs in standard mode — no
tracing agent, no conditional metadata — so anything the closed world cannot reach or
register fails the build instead of surfacing at runtime, and the executable is built with
`--no-fallback`, so there is no JVM fallback to mask a missed registration. No production
native-image metadata is committed today (production code uses no reflection, which the
architecture rules enforce); the only committed reachability input is the GraalVM
reachability-metadata repository described below, and any future committed metadata file
arrives reviewed, entry by entry, with the production code that needs it. The picocli
reflection registrations are generated at build time by `picocli-codegen` into
`META-INF/native-image/picocli-generated/` inside the built JAR — build output, never a
committed source file — and `checkPicocliNativeMetadata` fails the build when those
generated entries are missing from the packaged JAR.

### Verification-metadata completeness

Two drift guards keep `gradle/verification-metadata.xml` honest, because regenerating it
from a warm cache can silently under-cover the graph — cached artifacts are not
re-downloaded, so anything the run skipped never gains its entry and only a fresh clone
fails strict verification (exactly how the jackson-2 parent POMs of the test-scoped schema
validator once went missing):

- `verifyMetadataComplete` runs in every `check` and compares the committed metadata file
  against the committed lock state: a component pinned by `gradle.lockfile` or
  `settings-gradle.lockfile` without a metadata entry fails the build naming every gap.
- The CI dependency job resolves the tree in a virgin `GRADLE_USER_HOME`, where every
  artifact — parent POMs included, which sit outside both the lock state and Gradle's
  write-mode recording — downloads under strict verification.

Regenerating after a dependency change therefore takes a cold home plus a hand-completed
parent-POM entry where Gradle's write mode skips one. The file's policy is checksums only:
record `sha256` (not `pgp`) so verification never depends on keyserver availability, and
never let the write mode introduce a trusted-keys section — a file with keys starts
verifying signatures of artifacts whose signers were never vetted here:

```console
GRADLE_USER_HOME=$(mktemp -d) env -u GRAALVM_HOME mise exec -- \
  ./gradlew --no-daemon --write-verification-metadata sha256 \
  clean compileTestFixturesJava testClasses nativeSmokeTestClasses resolveAndLockAll
# a strict run in another fresh home then names any metadata-path artifact the write mode
# skipped (parent POMs); add its sha256 entry (of the freshly downloaded artifact) and
# re-prove until the strict run passes
GRADLE_USER_HOME=$(mktemp -d) env -u GRAALVM_HOME mise exec -- \
  ./gradlew --no-daemon --console=plain clean compileTestFixturesJava testClasses
```

### Reachability-metadata trust exception

One dependency-adjacent input sits deliberately outside that verification: the GraalVM
reachability-metadata repository (`metadataRepository.enabled`), fetched over the network
at native-image build time to supply reflection registrations for third-party libraries.
Gradle's dependency verification does not cover it, so the trust story is stated instead of
implied: the repository is consumed exactly as the pinned Gradle plugin resolves it, its
effect is confined to the native executable (never the JVM classpath), and the three release
platforms each rebuild the executable from the same tagged sources on the same pinned
toolchain, so a drifting metadata pull fails the platform verifications rather than
shipping silently. If the repository ever needs pinning or vendoring, that change is a
release-matrix decision recorded here first.

## Live protocol smoke

The JVM suite ships an **opt-in** live protocol smoke (`@Tag("live")`, package
`io.amscotti.bravesearch.adapter.bravehttp.live`): serial, bounded, protocol-invariants-only
exchanges against the production Brave origin. Default builds — including every CI run —
exclude the tag entirely, so `test` and `check` make zero external calls, and the live suite
is never required for a pull request.

To run it, make a credential resolvable in the shell (the canonical provider resolves
`BRAVE_API_KEY`, then the compatibility alias, then the secure config file; the developer
shell may source the local untracked `.env` to export it — that file never enters version
control and production code never reads it) and opt in with the explicit Gradle property:

```console
$ env -u GRAALVM_HOME mise exec -- ./gradlew --no-daemon --console=plain test -PliveBraveTests=true
```

The opt-in is a command-line `-P` flag and never persists in `gradle.properties` — a pinned
assertion of the gating test enforces this — because a committed property would silently
turn every local and CI build into a live, credentialed run. An IDE test launcher bypasses
the Gradle tag gate entirely (the exclusion lives in the build script), so an IDE run of the
test source set executes the live tests instead of excluding them; each one then skips
cleanly on the missing credential through the guard's fixed skip message, but the supported
invocation is the Gradle one above.

Without a resolvable credential every live test skips with the fixed message
`live tests require BRAVE_API_KEY`. The opted-in run is serial by policy: the test task pins
`maxParallelForks = 1` and every exchange holds the guard's class-level lock. The origin
enforces a one-request-per-second policy (observed as the `X-RateLimit` policy `1;w=1`
alongside a monthly window — `2000;w=2592000` was observed on the development key, recorded
as an observation, not a contract), so every dispatch rides the suite's shared pacing gate,
which spaces consecutive live exchanges at least 1.1 seconds apart. A dispatch that still
answers 429 is retried exactly once — test instrumentation, never product retry — after
waiting the window reset the failure's rate-limit snapshot observed, bounded to five
seconds; when the smallest applicable reset outlives that budget (an exhausted monthly
window, for example) the test skips with the fixed message `rate window requires a longer
wait than the smoke budget`, and a paced retry that answers rate-limited again skips the
same way with `rate limit persisted after the single paced retry`. Invariants hold
according to the plan entitlements the key
carries: every entitlement-gated probe — places, llm context, and both answers wire-form
probes — treats the documented entitlement-absence shape (HTTP 400 with upstream code
`OPTION_NOT_IN_PLAN`; live-observed on the development key for places, llm context, and
answers)
as a loud, recorded assumption skip with its fixed message (`place search is not included
in this plan`, `llm context is not included in this plan`, or `answers is not included in
this plan — the nested web_search_options probe requires an entitled key`), while any
other failure shape fails loudly. Each test
sends one inexpensive bounded request — web, context, and places searches at `count=1`, one
blocking answer capped at 32 completion tokens — and asserts protocol invariants only: the
exact endpoint path, HTTP 200, a JSON-object body, the web response's `web` object with its
`results` array, rate-limit windows, the nested `web_search_options` wire form, and the
`Api-Version` exchange as a recorded verdict — a 2xx records the pin as served (with any
offered `Api-Version` response header), while a 4xx answering upstream code
`API_VERSION_NOT_FOUND` records that the pin reached the server and was evaluated
(live-observed for the doc-baseline pin `2026-08-30`, which answered 404 on the development
key); no server default is hardcoded. Live result
contents are never snapshotted, printed, or stored; the only emitted observations are
bounded, redacted structural facts (counts, statuses, classifications), and no test output
ever carries the token or full request headers.

## CI matrix

Defined in `.github/workflows/ci.yml` and `.github/workflows/release.yml`, with their structure
pinned locally by `io.amscotti.bravesearch.release.WorkflowContractTest`. Every action reference is
pinned by the full commit SHA its tag resolves to on the GitHub API:

| Action | Pinned SHA | Resolved tag |
| --- | --- | --- |
| `actions/checkout` | `3d3c42e5aac5ba805825da76410c181273ba90b1` | v7.0.1 |
| `jdx/mise-action` | `c2a87611a18de5b3828c5652fe268e992400cb5c` | v4.3.0 |
| `actions/upload-artifact` | `330a01c490aca151604b8cf639adc76d48f6c5d4` | v5.0.0 |
| `actions/download-artifact` | `018cc2cf5baa6db3ef3c5f8a56943fffe632ef53` | v6.0.0 |
| `actions/github-script` | `3a2844b7e9c422d3c10d287c895573f7108da1b3` | v9.0.0 |
| `actions/attest-build-provenance` | `e4d4f7c39adfa4c260fb5c147f0622000aa14b99` | v4.0.0 |

The retired upstream wrapper-validation action is deliberately absent: upstream removed it
from `gradle/actions` and archived its standalone repository, so any reference fails the
hosted run before a build starts. Wrapper integrity rests on the wrapper itself, which
validates the distribution on every invocation against the SHA-256 pinned in
`gradle/wrapper/gradle-wrapper.properties`.

CI jobs: a full `clean check` on `macos-26`, `ubuntu-24.04`, and `ubuntu-24.04-arm` (with mise version, exact
Java pin, native-image path, and selected-executable assertions from the same `--info` check log),
the repository hygiene gate (including a tracked credential-file guard), the native
process smoke suite on `macos-26` (architecture asserted `arm64`), `ubuntu-24.04`
(architecture asserted `x86_64`), and `ubuntu-24.04-arm` (architecture asserted `aarch64`), and a dependency job that rewrites the lock state with
`--write-locks resolveAndLockAll` — so the following `git diff --exit-code` fails on both
drift and extraneous entries — resolves the tree in a virgin Gradle user home under strict
verification (parent POMs included), and performs a clean-cache strict-verification build.
CI runs one build per reference: a superseded run of the same branch or pull request is
cancelled in progress instead of racing for the same runners. The workflows deliberately
configure no Gradle caching: every run resolves and verifies dependencies from a clean
cache, so a stale cache can never mask dependency drift or a broken artifact source.
The heavy hosted builds and the nested sample-consumer build cap Gradle workers at two.
Linux JVM test jobs install Zsh for the completion-script syntax checks.

The hygiene job also executes the release resolver against offline GitHub API fixtures,
covering valid annotated tags, commit identity, maintainer accounts, signatures, and failed
CI checks. Run these workflow-specific tests locally with Node.js:

```console
node --test .github/tests/release.test.mjs
```

Releases trigger only on an annotated, signature-verified semantic-version tag (`v*.*.*`).
A tag push reports the target commit as `github.sha`. The resolver reads the annotated tag
object, requires it to point directly to a commit, and matches that target to the workflow
commit. The signature must verify on the GitHub API, which requires the
signing key to be registered to a GitHub account — a key GitHub does not know is reported
as an unverified signature with reason `unknown_key`, and the release refuses to run; a
verified signature alone proves only that some GitHub account holds the key, so the
release also requires the account that pushed the tag (`github.actor`) to be on the
maintainer allowlist, with the tag-target commit's author login (GitHub's
email-to-account association from the repository-commit API) on the same allowlist as a
secondary restriction. The raw Git database commit API does not return account logins. The
resolver also requires the commit's CI to
be green before anything else runs: every check-run display name ci.yml produces — each
matrix leg by its exact name, such as `jvm-check (macos-26)`, `jvm-check
(ubuntu-24.04)`, and `jvm-check (ubuntu-24.04-arm)` — must be present with conclusion success; check runs carry these bare
job display names, never a workflow-prefixed form, and one green leg never substitutes
for the other. Each platform builds its archive on its exact native runner with the same
mise pin and native-image assertions CI enforces; each platform-matched verification leg
downloads the packaged artifact, validates the staging `SHA256SUMS`, unpacks, checks the
executable mode and binary architecture, reruns `--version` and compares it against the
verified tag version, exercises a failure-path smoke, and uploads evidence. Only after
all legs succeed does the single privileged publisher job (the only one holding
`contents: write`) attest build provenance, generate the aggregate `SHA256SUMS` over
every archive and SBOM, and publish the release — per-platform
checksum files never ship as assets. Publication is re-runnable: `gh release create`
builds the release object before its assets upload, so a transient failure mid-upload
would otherwise strand a half-populated release that a re-run cannot recreate; the
publisher therefore creates the release only when it does not exist and uploads every
asset with `gh release upload --clobber`, replacing any half-uploaded file wholesale.
The publisher sets `GH_REPO` explicitly because it works from downloaded artifacts without
a repository checkout.

## Checksum-first install

Download the archive for your platform and the release's aggregate `SHA256SUMS`, verify
the archive **before** unpacking, then unpack and put the binary on your `PATH`. The
aggregate manifest covers every platform archive and SBOM of the release, so filter it to
exactly the file you downloaded; macOS example (substitute the version and platform):

```console
$ curl -LO https://github.com/amscotti/brave-search-cli/releases/download/v1.2.0/brave-search-1.2.0-macos-aarch64.tar.gz
$ curl -LO https://github.com/amscotti/brave-search-cli/releases/download/v1.2.0/SHA256SUMS
$ grep 'brave-search-1.2.0-macos-aarch64.tar.gz$' SHA256SUMS | shasum -a 256 -c -
brave-search-1.2.0-macos-aarch64.tar.gz: OK
$ tar -xzf brave-search-1.2.0-macos-aarch64.tar.gz
```

On Linux, use `sha256sum -c -` in the same pipeline. The `$` anchor keeps the filter to
the one archive — the manifest also lists the other platforms' archives and all SBOMs, so
an unfiltered `shasum -a 256 -c SHA256SUMS` fails for anyone who has not downloaded every
listed file. To verify the whole manifest instead of the filtered line, download every
file it lists (each platform archive and each SBOM) and run the unfiltered check — a
missing file is then itself a failure. If a digest does not match, do not run the binary.

## PATH setup

Add the unpacked `bin` directory to your shell's `PATH`, for example:

```console
$ mkdir -p ~/.local/brave-search && tar -xzf brave-search-<version>-<os>-<arch>.tar.gz -C ~/.local/brave-search
$ echo 'export PATH="$HOME/.local/brave-search/brave-search-<version>-<os>-<arch>/bin:$PATH"' >> ~/.zshrc
```

Shell completions ship inside the archive: source
`completions/brave-search.zsh` (Zsh) or `completions/brave-search.bash` (Bash), or regenerate
them for the installed binary with `brave-search completion bash` / `completion zsh`.

## macOS Gatekeeper and quarantine

The binaries are unsigned and not notarized (signing and notarization are deliberately
deferred until the release artifacts are stable), so Gatekeeper may block or warn on first
run of a downloaded binary. After verifying checksums and unpacking, remove the quarantine
attribute from the unpacked binary if your Mac flags it:

```console
$ xattr -d com.apple.quarantine ~/.local/brave-search/*/bin/brave-search
```

Only do this for a binary whose archive checksum you verified. Downloading with `curl`
instead of a browser usually avoids the quarantine attribute entirely.
